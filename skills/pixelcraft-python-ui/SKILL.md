# Pixelcraft Python UI

Use this skill when Python owns the UI layer. These frameworks differ radically: some produce DOM apps, some rerun scripts, some synchronize widgets, and some render native/canvas surfaces. Identify the execution/state model before visual design.

## Detection signals

`requirements.txt`, `pyproject.toml`, imports, app entry points, framework config (`.streamlit/config.toml`), notebook files, component constructors (`st.*`, `gr.*`, `rx.*`, NiceGUI `ui.*`, Dash layout callbacks, Panel objects, Shiny UI/server, Flet controls, Kivy KV, ipywidgets).

## Translate direction with honest constraints

1. Preserve the direction concept even when exact visual control is limited: hierarchy, real content, color posture, composition, copy, states, and data design still apply.
2. Map tokens through the framework's supported theme layer first; use custom CSS/components only as scoped escape hatches.
3. Understand rerun/session/callback semantics before designing interaction. Do not lose form state because a widget key or callback owner was careless.
4. Prioritize data legibility, task flow, feedback, empty/error states, and reproducibility over cosmetic pixel matching.
5. Escape hatch order: native theme config → semantic component props/layout containers → documented custom CSS/classes → custom component/extension. Avoid brittle selectors where docs warn DOM internals change.

## Platform-wide rules

- Do not fake a generic React dashboard when the framework's strength is rapid data/ML workflow clarity.
- Every expensive computation exposes progress, cancellation/timeout expectations, cache state, and failure recovery.
- Inputs have labels/help/format validation and preserve values across reruns/callbacks where possible.
- Tables/charts need text summaries, empty states, real units, appropriate color scales, and non-color encoding.
- Session state is explicit: inspect keys, initialization, stale cache, concurrency, and multi-user leakage.
- Secrets, uploaded files, generated files, and user data must not leak across sessions/users.

## Common Python-UI failures

- uncontrolled script reruns wiping input or triggering expensive work;
- hidden state keys colliding across pages/users;
- custom CSS selectors depending on unstable autogenerated classes;
- charts with no loading/error/empty data treatment;
- sidebar overloaded as navigation and control panel simultaneously;
- progress bars that fake progress or block interaction;
- wide desktop layout unusable in narrow embedded contexts;
- theming confined to primary color while hierarchy/state/copy remain default.

## Verification options

DOM-backed frameworks can often be inspected in browser when the app runs, but visual verification requires actually launching them. Unit tests may validate callbacks/state without proving rendering. Flet/Kivy need app/screenshot/device inspection. Jupyter widgets depend on kernel/frontend context. Label absence honestly; do not imply browser rendering happened because Python code compiled.
